# System Scalability and Architectural Audit Report

## Executive Summary
This report presents a comprehensive scalability audit of the application architecture, covering backend services (`server.ts`, `src/server/agent.ts`, `src/server/pdf-ai.ts`) and frontend client architecture (`src/App.tsx`, `src/store/useAppStore.ts`).

The analysis evaluates 9 core technical domains and estimates performance risks across 5 user concurrency tiers: **100**, **1,000**, **10,000**, **100,000**, and **1,000,000** concurrent users. All recommendations strictly preserve 100% backward compatibility with existing APIs, data models, and user workflows.

## Technical Audit Domains

### 1. Database Bottlenecks
* **Current State:** The application currently relies on transient, in-memory data structures (`useState` in `useAppStore.ts` on the client, and `Map` collections in `server.ts` on the server). There is no persistent database layer (e.g., PostgreSQL, MongoDB, Redis).
* **Identified Bottlenecks:**
  - **Lack of Central Persistence:** Data (customers, tickets, transactions, documents) is isolated to individual browser memory instances.
  - **No Multi-Node Sharing:** Without a centralized data store or cache layer, scaling horizontally across multiple server instances is impossible because state cannot be synchronized across nodes.
  - **Single-Thread Query Locking:** Operations requiring array filtering (e.g., `conversations.find()`, `notifications.filter()`) occur in memory on the V8 main thread.

### 2. Slow Queries
* **Current State:** Memory arrays in `useAppStore.ts` and `server.ts` perform linear array scans (`O(N)` lookups) for tickets, customers, transactions, and notification statuses.
* **Identified Bottlenecks:**
  - Linear array filtering on `serviceTickets.filter(t => t.status === 'waiting')` and `notifications.filter(n => !n.read)` executes on every render pass in React components.
  - In `server.ts`, proxy instances array filtering (`activeBases.filter(...)`) performs sequential string checks and timestamps calculations per incoming request without indexed fast-paths.

### 3. Repeated Rendering
* **Current State:** All React component views are statically imported at the top of `src/App.tsx`, creating a single monolithic bundle (~820kB). State updates in `useAppStore.ts` trigger top-level component re-renders.
* **Identified Bottlenecks:**
  - **Un-memoized State Derivations:** Values like `unreadNotifications`, `waitingTickets`, `activeJobs`, and `todayRevenue` are recalculated on every hook call without `useMemo`.
  - **Monolithic State Store:** Updating a single notification state causes subscribers across unrelated views to re-render.
  - **Lack of Code Splitting:** Heavy modules like code syntax highlighters and markdown renderers are loaded upfront rather than dynamically on route activation.

### 4. Expensive Loops
* **Current State:** File and media handling endpoints contain synchronous file system reads and repetitive parsing routines.
* **Identified Bottlenecks:**
  - `fs.readFileSync` calls in `src/server/agent.ts` and `src/server/pdf-ai.ts` block the Node.js event loop during heavy payload handling.
  - Sequential regex matching and string parsing during HTML/PDF scraping (`/api/scrape-exams` via Cheerio/Puppeteer) run across large DOM trees synchronously.

### 5. Unnecessary API Requests
* **Current State:** Frontend views issue polling and fallback requests across media search and PDF extraction services.
* **Identified Bottlenecks:**
  - **Cascading Fallbacks:** `/api/media/search` attempts up to 4 sequential/parallel scraper backends (local yt-dlp, youtube-sr, Piped nodes, Invidious nodes) when queries return partial or empty results.
  - **Un-cached External AI API Calls:** Chat requests to `/api/generate` issue external requests to Gemini/Groq/OpenRouter without local semantic or query hashing.

### 6. Caching Opportunities
* **Current State:** In-memory caching maps exist for media extraction (`extractionCache`) and PDF text (`pdfExtractionCache`), but are ephemeral and server-instance bound.
* **Identified Bottlenecks:**
  - **No Shared Distributed Cache:** Multi-process or clustered node instances cannot share cached media URLs or extracted PDF text.
  - **Unbounded Memory Map Size:** `extractionCache` in `server.ts` stores entries with an expiration timestamp but lacks an active max-size eviction policy (e.g., LRU).

### 7. Memory Growth
* **Current State:** Unbounded Map structures and process buffer allocations present memory leak risks under high load.
* **Identified Bottlenecks:**
  - **Unbounded Maps:** `extractionCache`, `offlineInstances`, `extractRateLimits`, and `streamRateLimits` in `server.ts` retain keys dynamically.
  - **Buffer Accumulation:** Buffer objects generated by `sharp`, `pdf-lib`, and `pdf-parse` in `agent.ts` and `pdf-ai.ts` linger in heap memory prior to garbage collection cycles.

### 8. CPU Intensive Tasks
* **Current State:** Headless browser automation and media binary executions run directly within the main Express server process context.
* **Identified Bottlenecks:**
  - **Puppeteer Headless Chrome Launches:** Endpoint `/api/scrape-exams` and `/api/pdf-ai/generate` launch Puppeteer Chromium instances per request, consuming 100-300MB RAM and significant CPU per process.
  - **Child Process Executions:** Synchronous/asynchronous `execAsync` calls running `yt-dlp` and Node.js sandbox scripts (`agent.ts`) create significant OS process creation overhead.

### 9. Background Job Improvements
* **Current State:** Long-running workflows (PDF compilation, image cropping, external API racing) execute synchronously within the HTTP request/response cycle.
* **Identified Bottlenecks:**
  - HTTP client connections remain open while Puppeteer compiles PDFs or Gemini generates code scripts, risking socket timeouts under queue backup.
  - Absence of a background task worker queue (e.g., BullMQ / Redis worker threads) forces the web server to act as both request broker and job processor.

## Future Risk Estimation Across User Tiers

| User Concurrency Tier | Risk Profile & Analysis |
| :--- | :--- |
| **100 Concurrent Users** | **Low Risk:** Current single-process Express setup easily handles 100 concurrent users. In-memory arrays in React store perform well. |
| **1,000 Concurrent Users** | **Moderate Risk:** Simultaneous Puppeteer launches (`/api/pdf-ai`) or media extractions will saturate CPU cores. Memory usage will spike due to simultaneous stream proxy buffers. |
| **10,000 Concurrent Users** | **High Risk:** Event loop blocking from synchronous file operations and `execAsync` process spawns will cause request queuing and HTTP 504 gateway timeouts. Single Node.js process memory ceiling (1.5GB default) will be threatened by unbounded caches. |
| **100,000 Concurrent Users** | **Critical Risk:** Architecture fails without horizontal scaling, external distributed database (PostgreSQL/MongoDB), and multi-node caching (Redis). Browser clients suffer rendering slowdowns from state growth in `useAppStore`. |
| **1 Million Concurrent Users** | **Catastrophic Failure:** Requires microservice decomposition, dedicated worker pools for Puppeteer/yt-dlp, CDN edge caching for media stream proxies, and complete separation of frontend state from monolithic memory stores. |

## Prioritized Improvements (Ranked by Impact)

1. **High Impact: Asynchronous Worker Queue for Heavy Tasks**
   - Offload Puppeteer PDF rendering, Sharp image processing, and yt-dlp binary extractions to a dedicated background worker queue (e.g., Redis + BullMQ).
2. **High Impact: Persistent Database Integration**
   - Introduce a persistent relational/document store (e.g., PostgreSQL or MongoDB) with indexed lookups to replace transient client/server in-memory state arrays.
3. **Medium Impact: Distributed Caching Strategy**
   - Implement an LRU bounded cache backed by Redis for `/api/media/extract` and `/api/pdf-extract` results to enable horizontal scaling across multiple web instances.
4. **Medium Impact: React Code Splitting & State Optimization**
   - Implement `React.lazy` and `Suspense` dynamic imports for secondary tab views in `App.tsx`. Memoize derived state lookups in `useAppStore.ts` using `useMemo` and `useCallback`.
5. **Low Impact: Stream Disconnect & Memory Cleanup Guards**
   - Add explicit stream cleanup listeners (`res.on('close')`) to terminate upstream proxy requests immediately when clients abort media streams.
