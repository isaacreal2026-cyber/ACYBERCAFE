# Security Audit & Recommendations Report

This document outlines the security audit findings for the CyberPlus Operations Center full-stack codebase. The audit covers ten key vulnerability areas, highlights active risks, and details minimal security fixes that do not alter the core application logic.

---

## 1. Cross-Site Scripting (XSS)

* **Status:** Low Risk in Frontend; Medium Risk in Headless Browser.
* **Findings:**
  - The React frontend handles data rendering using standard curly-brace JSX interpolation `{}` which auto-escapes string values.
  - No occurrences of `dangerouslySetInnerHTML` or raw `innerHTML` properties were discovered in the user-facing source code.
  - **Headless PDF Rendering Risk:** In `src/server/pdf-ai.ts`, dynamic HTML text generated by OpenAI (`gpt-4o`) is passed to Puppeteer:
    ```typescript
    let htmlContent = response.choices[0].message.content || "...";
    ...
    await page.setContent(htmlContent, { waitUntil: "domcontentloaded" });
    ```
    If an attacker crafts an input prompt that forces the LLM to reflect `<script>` tags, Puppeteer will load and execute the scripts under the local host/container context. Because Puppeteer is launched with `--no-sandbox` to run inside the container, any active script execution increases host compromise risk.
* **Minimal Recommended Security Fix:**
  - Disable JavaScript execution inside Puppeteer since it is only being used to format static HTML documents into PDFs:
    ```typescript
    const browser = await puppeteer.launch({
      args: ["--no-sandbox", "--disable-setuid-sandbox"],
    });
    const page = await browser.newPage();
    await page.setJavaScriptEnabled(false); // Completely disables script execution inside PDF pages
    ```

## 2. SQL Injection

* **Status:** Safe.
* **Findings:**
  - The application is a file-based/in-memory state machine. It does not integrate any relational database packages (such as `sqlite3`, `pg`, `mysql2`).
  - Client state is managed on the frontend using React hooks (`useAppStore.ts`), and temporary server state is held in native ES6 `Map` variables in `server.ts`.
* **Minimal Recommended Security Fix:**
  - No action required. If SQL databases are introduced in the future, parameterised queries or standard Object-Relational Mappings (ORMs) must be enforced.

---

## 3. NoSQL Injection

* **Status:** Safe.
* **Findings:**
  - The codebase does not communicate with NoSQL databases (e.g., MongoDB, DynamoDB).
  - Caches and rate limit lists are stored in standard in-memory structures without a query engine layer.
* **Minimal Recommended Security Fix:**
  - No action required.

---

## 4. Cross-Site Request Forgery (CSRF)

* **Status:** Safe.
* **Findings:**
  - The application is designed around state-free APIs. It does not implement cookie-based session management.
  - Since APIs do not read state from ambient browser cookies, they are naturally resilient against CSRF vectors.
* **Minimal Recommended Security Fix:**
  - No action required under the current architecture. If cookie-based auth is implemented later, standard anti-CSRF token patterns and `SameSite` cookie restrictions must be set.

## 5. Authentication Weaknesses

* **Status:** High Risk.
* **Findings:**
  - **Bypassed Middleware Verification:**
    - In `server.ts`, the `validateApiKey` middleware is a placeholder that permits all incoming traffic without performing any verification:
      ```typescript
      const validateApiKey = (
        req: express.Request,
        res: express.Response,
        next: express.NextFunction,
      ) => {
        return next();
      };
      ```
    - Critical endpoints—`/api/media/extract`, `/api/ytdl-core/info`, and `/api/yt-dlp/info`—are mounted with this bypassed middleware. As a result, anyone can trigger resource-heavy YouTube parsing and stream proxying without an API key, exposing the host to quota drain and proxy abuse.
* **Minimal Recommended Security Fix:**
  - Update `validateApiKey` in `server.ts` to inspect the `X-API-Key` header (or query param) and reject unauthenticated requests:
    ```typescript
    const validateApiKey = (
      req: express.Request,
      res: express.Response,
      next: express.NextFunction,
    ) => {
      const apiKey = req.headers["x-api-key"] || req.query.apiKey;
      const secureKey = process.env.VITE_MEDIA_PROXY_API_KEY || "media_secret_secure_key_2026";
      if (!apiKey || apiKey !== secureKey) {
        return res.status(401).json({ error: "Unauthorized access: Invalid or missing API Key" });
      }
      return next();
    };
    ```

## 6. Authorization Bypass

* **Status:** High Risk (Remote Command Injection).
* **Findings:**
  - **Git Client API Shell Injection (`/api/git` in `server.ts`):**
    - The Git Client endpoint accepts `command` and an array of `args` in the request body.
    - Although the `command` is restricted to an allowed list (`['status', 'log', 'pull', 'push', 'commit', 'add']`), user arguments are formatted with custom quotes escaping and concatenated directly into an `exec` shell string:
      ```typescript
      let gitArgs = "";
      if (args && Array.isArray(args)) {
        gitArgs = args.map((a) => `"${a.replace(/"/g, '\\"')}"`).join(" ");
      }
      ...
      const { stdout, stderr } = await execAsync(`git ${command} ${gitArgs}`);
      ```
    - Enclosing shell arguments in double-quotes does **not** suppress command substitution (`$()`, \` \`) or variable expansion inside Unix shells like Bash.
    - An attacker can supply a malicious argument (e.g., `"$(id)"` or `"\`id\`"`) which the shell evaluates during execution, leading to remote command execution under the node context.
  - **Agent Sandbox Script execution (`src/server/agent.ts`):**
    - The agent router writes AI-generated code directly to `/tmp/agent_uploads` and executes it on the host filesystem via `execAsync('node ' + scriptPath)`.
    - If the LLM is compromised via prompt injection, an attacker can execute arbitrary host commands with the system privileges of the application process.
* **Minimal Recommended Security Fix:**
  - **For the Git Client Endpoint:** Replace `exec` with `execFile` or `spawn` to pass arguments directly to the binary as an array of literal strings, completely bypassing shell compilation and argument injection:
    ```typescript
    import { execFile } from 'child_process';
    import { promisify } from 'util';
    const execFileAsync = promisify(execFile);
    ...
    // Secure Parameter execution
    const { stdout, stderr } = await execFileAsync('git', [command, ...args]);
    ```
  - **For the Agent Script Executor:** Execute AI-generated code inside a restricted sandboxed context (e.g., using a library like `isolated-vm` or running inside an ephemeral, low-privileged Docker container) instead of executing raw commands on the host filesystem.

## 7. Exposed Secrets

* **Status:** Medium Risk.
* **Findings:**
  - Real, hardcoded Firebase client configurations and API keys are included in `src/lib/firebase.ts` and `firebase-applet-config.json`:
    ```json
    "apiKey": "AIzaSyA21gt4v-p7aZOTDPsslMMzme3HrcQ6Szk"
    ```
  - While Firebase configuration details are client-facing, embedding them as static variables in source files committed to a git repository risks leaking credentials to automated scanners and scrapers.
* **Minimal Recommended Security Fix:**
  - Load the client keys dynamically using Vite's environment variables (`import.meta.env.VITE_FIREBASE_...`):
    ```typescript
    const firebaseConfig = {
      projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
      appId: import.meta.env.VITE_FIREBASE_APP_ID,
      apiKey: import.meta.env.VITE_FIREBASE_API_KEY,
      authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
      storageBucket: import.meta.env.VITE_FIREBASE_STORAGE_BUCKET,
      messagingSenderId: import.meta.env.VITE_FIREBASE_MESSAGING_SENDER_ID
    };
    ```

## 8. Unsafe Storage

* **Status:** Low Risk.
* **Findings:**
  - The server creates files in `/tmp/agent_uploads/` and `dist/outputs/`.
  - While cleanups are executed inside standard `finally` blocks for `/process` and `/edit`, any unhandled error during processing could leave temporary files accumulated in storage.
* **Minimal Recommended Security Fix:**
  - Configure a cron job or background interval in `server.ts` to periodically prune temporary upload directories:
    ```typescript
    setInterval(() => {
      // Periodic pruning of /tmp/agent_uploads/
    }, 1000 * 60 * 60); // Clean hourly
    ```

## 9. Token Leaks

* **Status:** Safe.
* **Findings:**
  - Sensitive tokens or parameters are not stored in unencrypted browser storage (localStorage/sessionStorage).
  - API keys are not sent via referrer-leaking query parameters on standard navigation pathways.
* **Minimal Recommended Security Fix:**
  - Ensure any future payment tokens, Firebase credentials, or session IDs are transferred strictly using HTTP headers rather than URL query parameters.

---

## 10. Insecure API Endpoints

* **Status:** Medium Risk.
* **Findings:**
  - **No-Sandbox Headless Browsers:**
    - Puppeteer is launched with `--no-sandbox` across PDF generation and scraper routes. This parameter disables Chrome's process-level isolation, meaning a security flaw in Chrome can result in full container takeover.
  - **SSL Certificate Verification Bypass:**
    - Custom fetch wrappers and downloader helpers use `rejectUnauthorized: false` to allow connecting to target servers with invalid or self-signed certificates. This leaves connections vulnerable to Man-In-The-Middle (MITM) attacks where third parties can substitute file contents or alter API payloads.
* **Minimal Recommended Security Fix:**
  - Avoid using `rejectUnauthorized: false` for external API and video/file downloading. Set up proper CA root certificates inside the Docker container or local environment instead.
  - Run the node process under a non-root user and enable Chrome sandboxing where possible.
